# 打断预录音与补传

## 数据流与职责

`feed_Task` 持续采集麦克风，AFE 处理回声后，`detect_Task` 将每个单声道 PCM 帧放入
`wake_word.c` 管理的 PSRAM ring buffer。播放时不上传麦克风，但保留最近约 1.5 秒录音。
当前每帧 512 samples、16 kHz，按整帧向上取整后为 47 帧 / 1504 ms。

确认打断的处理顺序：

1. 检测任务先保留历史并写入本次确认帧，设置缓存保护，再发布 `EV_AUDIO_BARGE_IN`。
2. 主任务停止旧播放并处理取消确认。即使主任务仍等待播放锁、状态仍是 `PLAYING`，
   检测任务也只追加新录音，不再按 1.5 秒窗口裁掉句首。
3. 恢复 `LISTENING` 后，`audio_in` 在首次读取前获取缓存快照，按 FIFO 顺序编码、上传。
   新录音继续追加到同一队列，无需复制整段音频或拼接两条音频流。
4. 成功发送的 Opus 包覆盖快照中的全部采样后，解除本次保护。恢复检测锁存与解除
   缓存保护是不同操作，不能在恢复监听时提前解除保护。

`audio_preroll_policy.h` 存放保留时长和帧数裁剪策略；`wake_word.c` 负责队列、保护和清空；
`audio_in.c` 负责实际发送进度。`barge_in_guard.h` 单独负责播放期间的人声确认策略。
WebSocket 连接周期沿用原有逻辑。

## 播放期间的打断确认

参数集中在 `main/barge_in_guard.h`，按 16 kHz 的实际采样数计时：

| 参数 | 当前值 | 作用 |
| --- | --- | --- |
| 播放起始保护 | 1200 ms | 起播期间不累计打断候选 |
| 有效人声能量门限 | 12000 | 同时要求 AFE VAD 判为人声；不是分贝值 |
| 有效人声累计 | 480 ms | 只累计同时满足 VAD 和能量要求的音频 |
| 单次弱音/停顿上限 | 96 ms | 当前 32 ms/帧，允许最多连续 3 帧不达标 |
| 候选总窗口 | 640 ms | 从第一帧达标人声计时，包含所有弱音和停顿 |

原来任意一帧不达标就清零，音节之间的短暂停顿也会迫使用户重新累计连续 480 ms。
现在短隙只暂停人声累计，恢复达标人声后接着累计；连续间隙超过 96 ms，或者总窗口
超过 640 ms，仍清零并从下一帧重新收集。确认只会发生在达标人声帧上，间隙不增加人声量。
例如 256 ms 人声 + 64 ms 弱音 + 224 ms 人声，可以在总长 544 ms 时确认。
同一候选内全部间隙合计最多 160 ms，零散声音不能跨很长时间拼成一次打断。

确认后沿用 `s_barge_pending` 锁存，取消旧回答期间不重复发事件；恢复监听后重置锁存。
缓存保护及约 1.5 秒句首补传仍按上述流程工作，候选总窗口小于预录音窗口。
本次没有降低能量门限、缩短所需人声量或移除播放起始保护，也没有调整 AEC 模型和参数。
若用户整句话始终低于能量门限，短隙容忍也不会触发打断；需要结合真机日志进一步评估。

## 容量、线程和生命周期

- 使用 `vRingbufferGetInfo()` 的未读项数计算 PCM 量。禁止用总容量减去
  `xRingbufferGetCurFreeSize()`：NOSPLIT 的后者是当前可写单项大小，空队列也最多约为半个缓冲区。
- 所有生产帧大小必须等于 AFE fetch 帧大小，因此未读项数乘以每帧采样数即为真实待传采样数。
- 缓存保护字段和生产端裁剪在 `s_audio_buffer_lock` 内访问。消费者先复制一帧并归还
  ring buffer 项，再执行编码/网络发送，不在网络阻塞期间占着该项。
- 缓存仍为约 10.24 秒 / 330240 字节，覆盖约 1.5 秒预录音和最长 8 秒取消等待。
  没有增加大型音频缓冲。极端溢出时保护旧句首、丢弃新帧，并记录丢弃量。
- 补传批次号用于防止旧任务解除新批次保护；正常清空、重连和 AFE 模式切换同时清除保护。
- 先获得缓存锁，再挂起 AFE 任务进行模式切换，避免挂起持锁任务造成死锁。
- “补传成功”表示 WebSocket 发送接口成功接收这些包，不代表服务端已完成识别或作答。

## 日志与真机验收

一次正常打断应依次出现：

```text
Barge-in confirmed: energy=... min=... max=... speech_ms=480 window_ms=544 gaps_ms=64
Barge-in pre-roll protected: id=... frames=47 audio_ms=1504
Cancel acknowledged; resume buffered microphone audio
Barge-in replay start: id=... pcm_frames=... audio_ms=...
Barge-in replay sent: id=... audio_ms=... opus_frames=... dropped_ms=0
```

`replay start` 包含等待取消期间追加的录音，因此时长可以大于 `pre-roll protected`。
PCM 为 32 ms/帧、Opus 为 20 ms/包，末包可能包含少量实时音频，不能按两个帧数直接比较。
若出现 `replay incomplete` 或 `buffer full`，需要检查上传失败、会话结束或网络积压。

播放中有候选但尚未确认时，最多每两秒打印一条 `Barge-in pending`：

- `reason=startup_guard`：尚在播放起始保护期。
- `reason=low_energy/not_speech`：尚无达标候选；可同时看 `vad` 和 `energy`。
- `reason=collecting/short_gap`：正在累计，或暂时保留进度等待短隙结束。
- `reason=gap_expired/window_expired`：单次间隙或候选总长超限，计数清零。
- `reason=invalid_frame`：当前帧长度无效，计数清零。

`speech_ms`、`window_ms`、`gap_ms` 的箭头分别表示本帧处理前后的人声累计、候选总长和
当前连续间隙。`confirmed` 中的 `gaps_ms` 则是本次候选的全部间隙总长。
诊断日志是限频采样，不能还原所有尝试，也不能单凭一条 VAD/能量日志区分用户声音和回声。

烧录后至少检查：

- 回答中说“没问题了”“可以结束了”等短句，确认句首可被理解。
- 回答中说较长的补充内容，确认没有句首缺失、重复或前后倒序。
- 连续打断多轮，确认批次号变化、`dropped_ms=0`，并可以继续问答。
- 冷启动后的首次回答中，在起播保护期之后用正常语速说带音节停顿的短句，
  对比首次和后续打断是否都能一次触发。不同距离、音量下各测试数轮。
- 不主动讲话时让设备完整回答，检查预录音是否包含残余回声导致误识别。
- 无输入一分钟后重新唤醒，确认没有上一轮缓存混入。
- 网络异常或取消等待较长时，检查完整补传或明确的失败日志。

播放开始后的 1200 ms 仍属于原有误打断保护期，短句若完全落在该时间内可能不会触发打断。
原有句首保留修复与本次短隙容忍是两个独立环节，均需真机验证，不能由编译通过推断声学效果。

## 编译期回归

在 ESP-IDF 终端执行：

```powershell
xtensa-esp32s3-elf-g++ -std=c++17 -Wall -Wextra -Werror -fsyntax-only tests/audio_preroll_checks.cc
xtensa-esp32s3-elf-g++ -std=c++17 -Wall -Wextra -Werror -fsyntax-only tests/barge_in_guard_checks.cc
idf.py build
```

第一条命令使用实际保留策略检查长播放、延迟取消、FIFO 衔接、正常监听及容量溢出场景。
第二条命令使用实际打断策略检查短隙、长停顿、窗口边界、低能量/非人声、起播保护、
多轮重置及不同帧长；所有断言在编译期执行。
这是编译期策略验证，不能代替真实 FreeRTOS 并发、AEC 和 ACOS 服务端的真机测试。
