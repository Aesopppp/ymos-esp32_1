## 1. 产品概述

### 1.1 背景与目标

设计一款基于 ESP32-S3-Korvo-2 开发板的智能语音辅助设备，部署于客服/销售坐席工作台场景。设备挂在坐席耳机旁，实时监听用户（客户）说话，将语音流通过 Wi-Fi 经 WebSocket 实时传输至坐席辅助平台，供后台 ASR + AI 分析使用，实现"实时通话辅助"能力。

### 1.2 产品定位

| 维度 | 说明 |
|------|------|
| 角色 | 坐席侧语音采集终端（单向：用户 → 设备 → 平台） |
| 部署位置 | 坐席工位，靠近用户麦克风区域 |
| 核心价值 | 将客户语音实时流转写，为坐席辅助 AI 提供实时输入 |
| 目标用户 | 客服/电销坐席，及其后台 AI 辅助系统 |

### 1.3 关键约束（P0 范围）

- **P0 设备为纯采集端**：仅采集客户语音上行，不做语音合成/TTS 下行
- 网络依赖 Wi-Fi，需支持企业网络或热点接入
- 设备固件通过 WebSocket 传输 PCM 原始音频流
- 唤醒词仅用于本地设备状态指示（灯/日志），不影响录音本身
- **P1 扩展**：设备增加 TTS 音频流接收 + 扬声器/耳机播放能力（详见 §1.4）

## 1.4 产品路线图与分期计划

### 1.4.1 分期目标

| 阶段 | 核心价值 | 设备角色 | 音频方向 | 平台链路 |
|------|---------|---------|---------|---------|
| **P0（本期）** | 实时采集客户语音，辅助坐席 | 纯收音终端 | 客户 → 设备 → 平台（单向）| ASR → RAG → LLM → **PC 端话术展示** |
| **P1（下期）** | 在 P0 基础上，AI 建议通过语音播报给坐席 | 收音 + 播放终端 | 双向（上行采集 + 下行 TTS）| ASR → RAG → LLM → **TTS → 设备播放** |

### 1.4.2 P0 详细范围

**设备侧（本期必须交付）：**
- 唤醒词检测 → 进入 Listening 态
- 采集客户语音（16kHz / 16bit / 单声道 PCM）
- WebSocket 上行音频帧到坐席辅助平台
- 绿色 LED 指示 Listening 态（录音告知）
- 配置管理、OTA 升级、异常告警

**平台侧（本期必须对接）：**
- WebSocket 服务端（接收设备音频流）
- ASR 实时转写（接收 PCM → 输出文本）
- RAG 知识检索（根据 ASR 文本查询知识库）
- LLM 生成推荐话术
- **PC 端 UI 展示**推荐话术给坐席

**P0 明确不包括：**
- ❌ 设备端 TTS 播放
- ❌ 平台向设备推送音频流
- ❌ 双向对话（坐席说话由设备采集）

### 1.4.3 P1 详细范围

**设备侧（本期预留协议，P1 实现）：**
- WebSocket 接收平台下行的 TTS 音频流
- TTS 音频解码（PCM / Opus / MP3，需确认）
- 扬声器外放 或 有线耳机收听（Korvo-2 ES8311 DAC + NS4150 功放）
- 播放状态反馈（LED 变化、播放完成事件上报平台）
- 播放音量控制（硬件音量键 + 软件音量 NVS 配置）

**平台侧（P1 需扩展）：**
- LLM 输出 → TTS 合成（选择 TTS 引擎：阿里云 / 科大讯飞 / 自研）
- TTS 音频流通过同一 WebSocket 连接推送给设备
- 推送策略：实时流式（边合成边推送）或整句合成后推送
- 坐席可选择"仅看话术（PC）"或"听语音播报（设备耳机）"

**P1 明确不包括：**
- ❌ 全双工实时对话（坐席和客户同时说话，AI 实时干预）
- ❌ 客户直接听到 AI 播报（仅坐席侧耳机/扬声器）
- ❌ 设备端 ASR/意图识别

## 2. 音频通路决策（必读）

> ⚠️ 本节需在研发启动前与业务方确认，**一旦选定将影响固件架构**，改动代价大。

### 2.1 麦克风选型

| 选项 | 说明 | 推荐 |
|------|------|------|
| **A. 板载双麦（ES7210）** | Korvo-2 板载左/右双麦，间距约 7cm，支持双麦降噪/波束成形 | ⭐ 本期推荐 |
| B. 外接 I²S 咪头 | 通过 GPIO 接一颗 I²S 数字麦克风，位置更灵活 | 后期可扩展 |
| C. USB 麦克风 | 走 USB AUDIO CLASS，延迟高，不推荐 | ❌ 不推荐 |

**决策项：坐席场景下，客户距离设备约 30~80cm，是否需要双麦远场增强（波束成形）？**

- 若**不需要** → ES7210 配置为**单左麦模式**，简化固件，功耗更低
- 若**需要** → ES7210 配置为**双麦模式**，固件接入 ES7210 AEC 参考通道

### 2.2 回声消除（AEC）需求

Korvo-2 的 ES7210 AEC 参考输入引脚已预留，但：

| 场景 | 是否需要 AEC |
|------|-------------|
| 坐席戴耳机，设备在桌上（客户说话声为主） | **不需要 AEC**，耳机隔离了扬声器回声 |
| 坐席戴耳机，但设备在耳机嘴边 | 建议开启 AEC 参考，防止耳机漏音 |
| 扬声器外放（如免提场景） | 必须开启 AEC |

**决策项：本期是否默认开启 AEC？（影响 ES7210 配置和固件音频通路）**

### 2.3 提示音方案

Korvo-2 板载 NS4150 功放 + 扬声器接口，用于播放本地提示音：

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 设备本地播放提示音 | 唤醒成功/失败播放 TTS 或 wav | ⭐ 推荐（体验更好） |
| B. 不播放任何提示音 | 纯 LED 反馈，设备完全静默 | 坐席戴耳机时无感知 |
| C. 平台下发提示音流 | 通过 WebSocket 接收并播放 | 增加固件复杂度 |

**决策项：唤醒成功/失败是否需要本地提示音？（影响固件音频输出通路是否启用）**

### 2.4 音频格式平台对齐

> ⚠️ 需与坐席辅助平台确认以下参数，一旦确认双方需同步修改。

| 参数 | 当前默认值 | 待确认值 |
|------|-----------|---------|
| 采样率 | 16000 Hz | **需平台确认**：支持 8k / 16k / 48k 中的哪些？ |
| 位深 | 16-bit signed LE | **需确认**：平台 ASR 期望 8-bit / 16-bit / 32-bit？ |
| 声道数 | 1（单声道） | **需确认**：是否支持多声道混音？ |
| 编码方式 | 原始 PCM（base64 JSON） | **需确认**：是否可改为 Opus 压缩（节省带宽）？ |
| 字节序 | Little-endian | **需确认**：平台解码端是否匹配？ |
| 采样格式 | 有符号补码 | **需确认**：无符号是否有影响？ |

### 2.5 音频抖动缓冲

为避免因 WebSocket 发包间隔抖动导致平台 ASR 异常，设备端需实现固定延迟 jitter buffer：

```
客户端行为（发送端）：
  采集 → 写入 buffer（含时间戳） → 按固定节拍（32ms 间隔）发送
  buffer 深度：默认 3 帧（约 96ms），可配置
  超过 buffer 深度的新帧：丢弃（防止延迟累积）
  低于水位：发送静音填充（CNG - Comfort Noise Generation）

平台端要求（待确认）：
  - 平台是否也需要 jitter buffer？
  - 允许的最大端到端延迟是多少？
```

### 2.2 硬件能力边界

- ✅ 支持 16kHz 单声道 PCM 采集
- ✅ 支持 Wi-Fi STA 模式连接网络
- ✅ 支持 WebSocket 客户端建连
- ✅ 支持 ESP32-S3 本地神经网络加速单元（vector instructions）运行唤醒词检测
- ⚠️ ESP32-S3 内存有限（512KB SRAM），固件需裁剪，不跑完整 ASR 模型
- ⚠️ 无本地存储录音能力（本期），流式传输是唯一出口

### 3.1 会话生命周期边界

| 触发条件 | 动作 | 设备响应 |
|---------|------|---------|
| 唤醒词命中 | 进入 Listening | LED 常亮，开始采音+推送 |
| 静默超时（默认 30s，可配置） | 返回 Sleep | LED 慢闪，停止采音 |
| 收到 `stop` 指令 | 立即返回 Sleep | 立即停止采音，日志记录原因 |
| 收到 `resume` 指令（Sleep 态） | 进入 Listening | 无视唤醒词，直接采音 |
| 网络断开 ≥ 10 次重试 | 进入异常态 | 红色 LED 快闪，日志记录 |
| 固件升级中 | 暂停所有业务 | LED 全灭，禁止操作 |

**唤醒词"你好小易"与"客户来电接通"的时序关系：**

| 方案 | 描述 | 推荐 |
|------|------|------|
| A. 唤醒词先于通话 | 客户说"您好小易"时坐席还未接听，设备先采集，平台记录此段音频 | ⭐ 推荐，采集完整 |
| B. 唤醒词后于通话 | 客户说话→坐席接听→设备等待唤醒词→唤醒后才采集 | 可能丢失关键前段 |
| C. 唤醒词与通话独立 | 设备不依赖通话状态，客户说话即开始采集，唤醒词仅用于设备状态指示 | 需要考虑隐私合规 |

**决策项：采用哪种会话时序方案？（影响隐私合规和平台数据处理逻辑）**

### 3.2 状态机

```
P0 状态机（本期）：

  ┌─────────┐   唤醒词命中    ┌─────────────┐
  │  Sleep  │──────────────▶│  Listening  │
  │ (低功耗) │               │  (采音+转发)  │
  └─────────┘◀──────────────┘─────────────┘
              静默超时(可配置，默认30s)
              或收到 stop 指令

P1 扩展状态机（本期预留，P1 实现）：

  ┌─────────┐   唤醒词命中    ┌─────────────┐
  │  Sleep  │──────────────▶│  Listening  │◀──┐
  │ (低功耗) │               │  (采音+转发)  │   │ 收到 tts_play
  └─────────┘◀──────────────┴─────────────┘   │ (保持 Listening)
              │                  │             │   同时播放
              │                  │             │   ↓
              │  静默超时/stop   │             ┌──────────────┐
              │                  │             │   Playing    │
              │                  │             │ (TTS 播放中)  │
              │                  │             └──────┬───────┘
              │                  │                    │
              │                  │            播放完成/tts_stop
              │                  │                    │
              └──────────────────┴────────────────────┘
                       返回 Sleep

状态说明：
  Sleep      — 关闭麦克风采样，Wi-Fi 保活，LED 绿色慢闪
  Listening  — 持续采集 PCM 并通过 WebSocket 发送，LED 绿色常亮（P0）
               P1：Listening 同时可接收 TTS 音频流并播放，LED 绿色常亮+橙色闪烁
  Playing    — P1 态：正在播放 TTS 音频流，LED 橙色常亮
               P1：Listening 和 Playing 可并发（边采集客户语音边播放 AI 建议）
  唤醒词命中后进入 Listening，开始采音并推送音频流
  静默 N 秒（可配置）或收到远端 `stop` 指令后返回 Sleep
  P1：播放队列支持多句，播放中收到新 tts_play 追加到队列，不中断当前播放

## 5. 非功能性需求

### 5.1 性能

| 指标 | 要求 |
|------|------|
| 唤醒响应延迟 | 从语音结束到首次 PCM 发送 < 500ms |
| 音频延迟 | 采集到 WebSocket 发送 < 100ms |
| WebSocket 重连时间 | 断开后 3s 内首次重试 |
| 固件大小 | 目标 < 4MB（含唤醒词模型） |

### 5.2 功耗

| 场景 | 电流/功耗参考 |
|------|---------------|
| Sleep（Wi-Fi 保活） | ~30mA @ 5V |
| Listening（采音+传输） | ~120mA @ 5V |
| 注：USB 供电 5V/2A 充足，电池续航非本期重点 | |

### 5.3 可靠性

- 连续运行 24h 无内存泄漏
- 网络抖动（5s 内）不导致固件崩溃
- 音频帧丢帧率（因网络原因）< 1%（在良好 Wi-Fi 条件下）

### 5.4 安全性

- Wi-Fi 密码和 Token 不明文暴露于日志
- WebSocket 优先使用 wss（TLS）
- OTA 升级包需校验 MD5 或签名

```json

// 帧头（8 字节小端序）：
//   [0-1]  session_id_len: uint16     — session_id 字符串长度
//   [2-5]  audio_len: uint32          — 本帧 audio_data 字节数
//   [6]    flags: uint8               — bit0=last_frame, bit1=key_frame
//   [7]    codec: uint8               — 0=pcm, 1=opus, 2=mp3
// 帧体：
//   [8..8+session_id_len-1]  session_id UTF-8 字符串
//   [8+session_id_len..]     audio_data 原始字节
//
// JSON 协商帧（每次流开始前发送）：
{
  "type": "tts_start",
  "session_id": "tts-s-001",
  "codec": "pcm",              // pcm | opus | mp3
  "sample_rate": 16000,
  "bits": 16,
  "channels": 1,
  "total_frames": 50,          // 预估总帧数（可选，-1 表示未知）
  "text_hint": "根据您的需求，建议您..." // 本句文本（可选，供调试）
}

// P1 TTS 控制指令（新）
{
  "type": "tts_control",
  "action": "stop",           // stop / pause / resume / set_volume
  "session_id": "tts-s-001",
  "volume": 0.8               // action=set_volume 时填写，0.0~1.0
}

// P1 TTS 完成通知（新）
{
  "type": "tts_end",
  "session_id": "tts-s-001",
  "reason": "completed",      // completed | stopped | error
  "ts": 1694856000000
}

// P1坐席侧选择反馈通道（新）
{
  "type": "mode_select",
  "mode": "voice",            // text_only | voice_only | both
  "ts": 1694856000000
}
```

### 7.4 P1 TTS 播放子状态机

```
Idle ──tts_start──▶ Streaming
                    │
                    ├──[音频帧持续到达]──▶ Playing
                    │
                    └──tts_end (completed)──▶ Idle

Playing ──tts_control(stop)──▶ Idle
Playing ──tts_control(pause)──▶ Paused
Paused  ──tts_control(resume)──▶ Playing
Playing ──[解码错误]──▶ Error ──> Idle
```

### 7.5 P1 关键设计决策（待确认）

| 决策项 | 选项 A（推荐）| 选项 B | 影响 |
|--------|------------|--------|------|
| TTS 编码格式 | PCM（无压缩，延迟最低）| Opus（节省带宽，需解码）| 影响固件解码模块和延迟 |
| 推送策略 | 流式（边合成边推送，延迟 ~500ms）| 整句合成完推送（延迟 ~2s）| 影响坐席体验 |
| 播放优先级 | 坐席说话时暂停 TTS，说完继续 | TTS 与坐席声音混音 | 影响通话质量 |
| 输出设备默认 | 扬声器外放（Korvo-2 NS4150）| 有线耳机（3.5mm 孔）| 隐私/场景适配 |
| 播放音量范围 | 固定 80%（避免扰民）| 可调 0~100%（NVS 存储）| 用户体验 |

## 8. 错误码字典

> 设备端错误码统一为字母前缀 + 数字，平台端返回的错误码格式见 §8.3。

### 8.1 设备端错误码（设备本地记录）

| 错误码 | 描述 | 严重等级 | 客户端（设备）应对策略 |
|--------|------|---------|----------------------|
| `E_WW_001` | 唤醒词模型加载失败 | 🔴 致命 | 停止业务，红色 LED 常亮，等待固件重刷 |
| `E_WW_002` | 唤醒词检测超时（模型异常） | 🔴 致命 | 重启唤醒词引擎模块，连续失败 3 次则重启设备 |
| `E_ADC_001` | I2S DMA 初始化失败 | 🔴 致命 | 红色 LED 闪烁，报错后进入死循环等待人工干预 |
| `E_ADC_002` | ES7210 响应超时（I2C 通信异常） | 🟡 警告 | 重试 I2C 初始化 3 次，超限后降级为单麦模式 |
| `E_ADC_003` | DMA buffer 溢出（采音过载） | 🟡 警告 | 跳过本帧，刷新 buffer，计数+1 |
| `E_WS_001` | WebSocket 连接失败（网络不可达） | 🟡 警告 | 阶梯退避重连（3s/5s/10s），最多 10 次 |
| `E_WS_002` | WebSocket 发送失败（连接断开） | 🟡 警告 | 立即切换 Sleep 态，重新走 E_WS_001 重连流程 |
| `E_WS_003` | 心跳超时（60s 未收到 pong） | 🟡 警告 | 主动断开连接，触发重连 |
| `E_WS_004` | 收到非法控制指令 JSON | 🟢 提示 | 丢弃，日志记录原始数据 |
| `E_OTA_001` | OTA 固件下载校验失败（MD5 不匹配） | 🟡 警告 | 停止升级，回滚到原固件，LED 橙灯闪烁 |
| `E_OTA_002` | OTA 分区写入失败 | 🔴 致命 | 回滚原固件，记录错误，启动后上报平台 |
| `E_WIFI_001` | Wi-Fi 连接失败（密码错误/路由不可达） | 🟡 警告 | 重连 3 次后进入 AP 配网模式 |
| `E_WIFI_002` | Wi-Fi 信号弱（RSSI < -75dBm） | 🟢 提示 | 日志记录，设备继续工作（可能影响音频质量） |
| `E_MEM_001` | 内存分配失败（heap 不足） | 🔴 致命 | 立即重启设备 |
| `E_NVS_001` | NVS 配置区读取失败 | 🟡 警告 | 使用默认配置，提示配置可能丢失 |

### 8.2 平台端错误码（服务端下发）

| 错误码 | 描述 | 设备端应对策略 |
|--------|------|--------------|
| `AUTH_TOKEN_INVALID` | 设备 Token 校验失败 | 停止发送音频，红色 LED 闪烁，提示联系管理员 |
| `AUTH_TOKEN_EXPIRED` | Token 过期 | 停止发送音频，尝试向平台请求刷新 Token |
| `SESSION_LIMIT` | 平台并发会话数超限 | 停止采音，等待 `resume` 指令 |
| `RATE_LIMIT` | 发帧频率超出平台限制 | 降低发帧频率（从 32ms 延长至 64ms/帧） |
| `SESSION_NOT_FOUND` | 会话 ID 不存在 | 重置会话状态，重新发起连接 |
| `FORBIDDEN` | 设备被平台禁用 | 停止所有业务，红色 LED 慢闪，等待管理员解禁 |
| `SERVER_INTERNAL` | 平台服务端内部错误 | 降级：停止采音进入 Sleep，日志记录，5min 后重试 |

### 8.3 错误日志字段规范

每条设备本地日志条目必须包含以下字段（便于平台汇总分析）：

## 9. 异常路径与降级策略

### 9.1 完整异常路径决策树

```
设备上电
  ├─ Wi-Fi 连接失败
  │    ├─ 重试 3 次 → 失败 → 进入 AP 配网模式（橙色 LED）
  │    └─ 成功 → 继续
  │
  ├─ 唤醒词模型加载失败 → 🔴 致命 → 红灯常亮，等待固件重刷
  │
  ├─ WebSocket 连接失败
  │    ├─ 重试阶梯退避（3s→5s→10s）最多 10 次
  │    │    ├─ 10 次内成功 → 恢复业务
  │    │    └─ 10 次后仍失败 → 进入"网络异常态"（绿灯快闪）
  │    └─ 连接成功 → 进入 Sleep
  │
  ├─ 采音中网络断开
  │    ├─ 立即停止采音 → 返回 Sleep
  │    └─ 触发重连（同上 WebSocket 重连流程）
  │
  ├─ 鉴权 Token 无效
  │    ├─ Token 过期 → 尝试刷新，失败 → 红色 LED 闪烁，等待人工
  │    └─ Token 被禁用 → 红色 LED 慢闪，等待管理员解禁
  │
  ├─ OTA 升级失败
  │    ├─ MD5 校验失败 → 回滚原固件，橙色 LED 闪烁
  │    └─ 分区写入失败 → 回滚原固件，重启后上报
  │
  └─ 内存耗尽 → 🔴 致命 → 立即重启设备
```

### 9.2 降级策略矩阵

| 异常场景 | 默认行为 | 降级行为（Grade Down） |
|---------|---------|----------------------|
| 网络抖动（< 5s） | 继续采音和发送 | 采音继续，发送暂停，buffer 缓存，超 96ms 丢弃 |
| 网络中断（> 5s） | Sleep + 重连 | Sleep + 降采样率重试（可选） |
| VAD 异常 | 正常 VAD | 关闭 VAD，持续发送（含静音帧） |
| 双麦 ES7210 异常 | 双麦模式 | 降级为单左麦模式 |
| 唤醒词引擎崩溃 | — | 连续失败 3 次 → 设备重启 |
| OTA 升级中收到 stop | 立即停止 | OTA 中止，回滚，停止采音 |
| 通话中收到 OTA 指令 | 拒绝执行 | **禁止在 Listening 态触发 OTA，必须 Sleep 态才可升级** |

### 9.3 OTA 升级窗口管理

```
设备状态约束：
  Sleep 态 ←→ 可触发 OTA
  Listening 态 ←→ 禁止触发 OTA

OTA 触发流程：
  1. 平台发送 `control: ota_start`
  2. 设备检查当前状态：
     ├─ Sleep → 允许升级
     └─ Listening → 拒绝，回复 { status: "rejected", reason: "in_session" }
  3. 升级完成后设备自动重启，无需手动确认
  4. 重启后上报 { type: "status", state: "sleep", firmware_version: "v1.x.x" }
```

## 11B. WebSocket 协议细节（补充）

### 11B.1 鉴权机制

```
首次连接流程：
  1. 设备上电 → Wi-Fi 连接成功 → NTP 同步
  2. 发起 WebSocket 连接（wss://server/platform/v1/ws）
  3. 首次握手 Header 携带鉴权信息：
     Authorization: Bearer <device_token>
     X-Device-ID: <device_id>
     X-Firmware-Version: <v1.x.x>
  4. 服务端返回 101 Switching Protocols → 连接建立
  5. 服务端下发 { type: "auth_ok", session_id: "..." }
```

| 字段 | 说明 | 安全要求 |
|------|------|---------|
| `device_token` | 设备鉴权 Token，固件烧录时写入 NVS | 不得出现在日志中；支持 OTA 更换 |
| `device_id` | 设备唯一标识（由 MAC 地址派生） | 公开字段 |
| `session_id` | 平台分配的会话 ID，每次连接重新生成 | 每次连接必须更新 |

### 11B.2 心跳与超时配置

| 参数 | 值 | 说明 |
|------|---|------|
| 心跳发送间隔 | 30s | 设备主动发送 heartbeat |
| 心跳响应超时 | 60s | 60s 内未收到 pong 则断开重连 |
| TCP keepalive | 启用 | 平台侧 ESP32 TCP keepalive 检测死连接 |
| WebSocket ping/pong | 启用 | 备用心跳机制 |
| 连接最大空闲时间 | 24h | 平台强制断开，需设备重新连接 |

### 11B.3 二进制帧 vs 文本帧

| 帧类型 | 格式 | 使用场景 |
|--------|------|---------|
| 文本帧（Text） | JSON 字符串 | **所有控制指令、心跳、状态帧** |
| 二进制帧（Binary） | 原始字节 | 预留：未来若改用 Opus 编码，使用二进制帧传输压缩音频 |

> **本期全部使用文本帧（JSON）**，二进制帧为后期扩展预留。

### 11B.4 断线重连策略

```
设备重连状态机：
  idle ──首次连接──> connecting
  connecting ──成功──> connected
  connecting ──失败──> retry_wait
  retry_wait ──等待退避──> connecting
  connected ──断开──> retry_wait

退避参数：
  第1次重试：等待 3s
  第2次重试：等待 5s
  第3次重试：等待 10s
  第4~10次重试：等待 10s（不再增长）
  第10次重试后：停止重连，切换"异常态"（LED 红灯快闪）

异常态恢复：
  - 等待 5 分钟后自动重新尝试重连
  - 或等待平台下发 reconnect 指令
  - 坐席手动重启设备
```

### 11C.1 企业 Wi-Fi 支持

| 项目 | 要求 | 备注 |
|------|------|------|
| 基础支持 | WPA2-PSK（家庭/小型办公 Wi-Fi） | 本期必须支持 |
| 企业网络 | WPA2-Enterprise（802.1X / RADIUS） | **待确认是否需要**，如需要则固件需集成 mbedTLS + EAP-TLS/PEAP |
| Captive Portal | 酒店/公共 Wi-Fi 跳转页面 | ❌ 不支持，设备不访问浏览器 |
| 静态 IP | 支持通过配置设置静态 IP/DNS | 配网页面支持 |

**决策项：是否必须支持企业 Wi-Fi（WPA2-Enterprise）？影响固件 Wi-Fi 库选型和产线配置流程。**

### 11C.2 弱网策略

| 网络状况 | 设备行为 |
|---------|---------|
| 丢包率 < 5% | 正常发送，无额外处理 |
| 丢包率 5%~20% | 启动前向纠错（FEC）：每 4 帧发送 1 帧冗余奇偶校验帧（预留，需平台配合） |
| 丢包率 > 20% | 暂停发送，buffer 缓存，静默超时后进入 Sleep |
| RTT > 1000ms | 降低发帧频率（32ms → 64ms），缓解拥塞 |
| 突发抖动（< 2s） | jitter buffer 吸收，音频连续性优先 |

### 11C.3 有线 Ethernet 支持

> Korvo-2 板载无 Ethernet 接口。本项目**不支持有线网络**，仅支持 Wi-Fi。

如未来需有线网络，需换用带 Ethernet 接口的开发板（如 ESP32-Ethernet-Kit）或通过 USB 外接 Ethernet 模块（评估功耗和成本）。

## 11G. 量产与运维（补充）

### 11G.1 设备唯一 ID 生成与烧录流程

```
产线烧录流程：
  1. 烧录固件（含默认 Wi-Fi 配置 OTA 地址）
  2. 首次上电 → 设备自动生成 device_id（基于 EFUSE MAC 地址）

  次版本：新功能，向后兼容
  修订版本：Bug 修复，向后兼容

示例：
  v1.0.0 — 初始版本
  v1.1.0 — 新增 OTA 灰度
  v1.1.1 — 修复 Wi-Fi 重连 bug
  v2.0.0 — 切换到 Opus 压缩（不兼容 v1.x）
```

### 11G.5 mgmt_token 工厂烧录（云管平台鉴权）

> 与 11G.1 的 device_token 并行烧录，**互不干扰**。

```
格式：sk-mgmt-<32hex>-<serial>
示例：sk-mgmt-a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6-k001
存储：NVS namespace "korvo_cfg" key "mgmt_token"
产线工具：tools/factory_burn.py 需新增 --mgmt-token 参数

产线烧录步骤（在 11G.1 基础上扩展）：
  1. 烧录固件
  2. 首次上电 -> 设备自动生成 device_id
  3. 设备向 ACOS 平台注册 -> acos_token
  4. 设备向云管平台注册 -> mgmt_token  <-- NEW P1
  5. 三元组 (device_id, acos_token, mgmt_token) 关联到工位
  6. acos_token + mgmt_token 同时写入 NVS（只读）
```

## 11H. 隐藏风险分析

> 以下风险在 PRD 初稿中容易被忽视，但对项目成败影响重大。

### 风险 #1：多设备并发冲击平台

| 风险 | 描述 |
|------|------|
| 问题 | 1000 台设备同时上线，平台 WebSocket 连接数 = 1000，长连接压力大 |
| 影响 | 平台服务器资源成本、连接管理复杂度大幅上升 |
| 应对 | 平台侧提前做连接数规划；设备端实现指数退避重连，避免惊群效应 |
| 建议 | 在 Open Issues 中明确设备规模（见 §12 OI-04） |

### 风险 #2：Wi-Fi 干扰与天线位置

| 风险 | 描述 |
|------|------|
| 问题 | 工位 Wi-Fi 信号被显示器（HDMI）、USB Hub、打印机干扰，RSSI 波动 |
| 影响 | 音频帧延迟抖动增大，ASR 转写质量下降 |
| 应对 | 设备摆放规范（见 §11E.2）；Wi-Fi RSSI < -75dBm 时设备上报告警 |
| 建议 | 实验室环境下做全工位 Wi-Fi 覆盖测试 |

### 风险 #3：内存碎片导致长期运行崩溃

| 风险 | 描述 |
|------|------|
| 问题 | ESP32-S3 内存有限（512KB SRAM），长时间运行（24h+）产生内存碎片 |
| 影响 | malloc 失败（E_MEM_001），设备重启，业务中断 |
| 应对 | 固件设计避免频繁 malloc；使用静态内存池；长时间运行测试（72h 压测） |
| 建议 | Phase 5 稳定性调优阶段必须包含 72h 连续压测 |

### 风险 #4：ASR 服务端音频帧乱序

| 风险 | 描述 |
|------|------|
| 问题 | WebSocket 帧在网络中乱序，平台 ASR 收到乱序帧导致转写错误 |
| 影响 | 坐席辅助话术推荐错误，误导坐席 |
| 应对 | 音频帧携带 `ts`（采集时间戳）和 `seq`（序列号），平台按时间戳排序后送 ASR |
| 建议 | 平台侧 jitter buffer 至少缓存 5 帧再做排序 |

### 风险 #5：企业 Wi-Fi 802.1X 认证

| 风险 | 描述 |
|------|------|
| 问题 | 多数企业使用 WPA2-Enterprise（用户名/密码 + RADIUS），ESP32-S3 需集成 mbedTLS + EAP |
| 影响 | 固件体积增大（+300KB+），认证交互复杂，企业网络策略可能阻断设备 |
| 应对 | 确认网络环境；如必须支持，提前评估 mbedTLS 对固件大小的压力 |
| 建议 | 首次部署优先使用热点/独立 SSID，规避企业 Wi-Fi 复杂度 |

### 风险 #6：OTA 升级窗口与通话冲突

| 风险 | 描述 |
|------|------|
| 问题 | 坐席通话中平台触发 OTA 升级，设备切换 Sleep 态导致辅助中断 |
| 影响 | 坐席通话辅助体验差，平台侧误以为设备故障 |
| 应对 | 固件强制约束：Listening 态禁止触发 OTA（见 §9.3）；平台侧 OTA 任务仅在坐席下班后批量执行 |
| 建议 | OTA 计划任务仅在 22:00~07:00 执行，避开业务时间 |

### 风险 #7：唤醒词误触发与隐私

| 风险 | 描述 |
|------|------|
| 问题 | 客户/背景音误唤醒（误唤醒率 5% 意味着每小时约 12 次），且客户不知情被录音 |
| 影响 | 隐私合规风险 + 平台收到大量无意义音频帧 |
| 应对 | VAD 过滤纯静音帧 + 唤醒后首帧前加 500ms 前导缓冲（保留"您好小易"本身）；设备 Listening 态绿色 LED 必须亮起 |
| 建议 | 启动阶段目标误唤醒率 < 3%，随着模型调优逐步降低 |

## 11I. 智能语音辅助设备云管理平台（补充 · P1）

> **背景**：当前设备只通过 WebSocket 连 ACOS AI 平台，没有独立的设备管理通道。
> 微信小程序控制、OTA、配置下发都需要一个独立的"控制面"通道。
> 本节定义云管平台与设备之间的协议与对接规格。

> **协议版本：v1.1（2026-09-24 更新）**
> - mgmt_token 格式从 sk-mgmt-<32hex>-<serial> 改为 sk-{device_code}-{32随机}
> - 生成算法从 HMAC-SHA256 改为 base62 真随机
> - 详细见 docs/protocol/auth-flow.md §4

### 11I.1 整体架构

```
┌────────┐    ┌─────────────────┐    ┌────────┐
│ 微信小程序 │ ←→ │ 云管平台 (智语辅)  │ ←→ │ ACOS AI  │
└────────┘    └─────────────────┘    └────────┘
                        ↔ MQTT over TLS (8883)
                        ↓
                ┌───────────────┐
                │  ESP32-S3 设备  │  (ACOS WS + 云管 MQTT)
                └───────────────┘
                         鉴权: acos_token  /  mgmt_token (独立烧录)
```

**两个独立通道**：

| 通道 | 用途 | 协议 | 鉴权 | 实时性 |
|------|------|------|------|--------|
| ACOS WebSocket | AI 对话, 音频流, wake | WebSocket+JSON/TLS | acos_token | 高 |
| 云管 MQTT | 配置/指令/OTA/状态 | MQTT 5.0/TLS | mgmt_token | 中 |

> **设计决策**：不复用 ACOS 通道。云管协议完全自主定义，不依赖 ACOS 团队配合。

### 11I.2 五大设计决策（已拍板）

| # | 决策项 | 选择 | 理由 |
|---|--------|------|------|
| 1 | 通道方案 | **新开 MQTT 到云管** | ESP-MQTT 内置; 比 WS 省内存 (~30KB)、省电; 支持 QoS |
| 2 | 鉴权 token | **独立 mgmt_token** | 与 acos_token 解耦; 工厂同时烧两个 token |
 | 3 | 协议字段 | **见 11I.3**（v1.1 已 review 闭环） | — |
| 4 | 异常上报 | **本期不做** | 暂不埋钩子, 专注配置 + OTA |
| 5 | OTA | **走云管 MQTT 通道** | 产线 OTA 是刚需 |

 ### 11I.3 协议字段定义（v1.1，2026-09-24 定稿）

**云 → 设备**（下行 · MQTT topic: `dev/{device_id}/cmd`）

```json
// 1. 配置更新
{"type":"config_update","settings":{"volume":60,"led_mode":"night","room_id":"bedroom","vad_enable":true,"barge_in_enable":true},"ts":1719300000}

// 2. 指令下发
// cmd: reboot | reset_wifi | play_tts | factory_reset
{"type":"command","cmd":"reboot","args":{"text":"你好"},"ts":1719300000}

// 3. OTA 推送
{"type":"ota","version":"v1.2.3","url":"https://ota.example.com/fw.bin","sha256":"a1b2c3d4...","size":1234567,"force":false,"ts":1719300000}
```

**设备 → 云**（上行 · MQTT topic: `dev/{device_id}/telemetry`）

```json
// 4. 鉴权（首次连接发送一次）
{"type":"auth","mgmt_token":"sk-K001-...","device_id":"korvo-001","fw_version":"v1.0.0"}

// 5. 配置状态上报
{"type":"config_report","settings":{"volume":60,...},"reason":"boot|cloud_update|local_change","ts":1719300000}

// 6. OTA 进度与结果
{"type":"ota_progress","phase":"downloading|verifying|applying|rebooting|ok|failed","percent":45,"error":"","ts":1719300000}
```

### 11I.4 MQTT 连接参数

| 参数 | 值 | 说明 |
|------|-----|------|
| Broker URL | `mqtts://mgmt.example.com:8883` | TLS 必开 |
| Client ID | `korvo-{device_id}` | 唯一 |
| Keepalive | 60s | ESP-MQTT 默认 |
| QoS | 下行 QoS 1, 上行 QoS 0 | 配置不丢即可 |
| Last Will | `dev/{id}/status` -> `{"online":false}` | 异常掉线平台感知 |
| 重连策略 | 指数退避 1s->2s->...->60s（封顶） | 避免风暴 |

### 11I.5 mgmt_token 工厂烧录

```
格式：sk-{device_code}-{32随机}        (v1.1 更新: 不再是 HMAC 导出，改为 base62 真随机)
示例：sk-K001-7n3k9x2v8q5w1r2t3y4u5i6o7p8a9s0d
存储：NVS namespace "korvo_cfg" key "mgmt_token"
工厂烧录脚本：tools/factory_burn.py 需新增 --mgmt-token 参数
```

> **详细格式与生成算法见** `docs/protocol/auth-flow.md` §4；烧录流程见 11G.5。
 > **管理员 API Key** （给人用的不同于设备 mgmt_token）见 `docs/protocol/auth-flow.md` §5、`docs/PRDs/PRD-cloud-platform.md` §5.2、§7。

### 11I.6 OTA 详细流程

```
[云管平台]                                  [ESP32-S3 设备]
    |                                              |
    | -- MQTT {type:"","ota",...} -->              | 1. 收到 OTA 消息, 校验版本号
    |                                              | 2. 检查本地状态:
    |                                              |    - 不在通话中
    |                                              |    - 电量 > 30%
    |                                              |    - 上次升级 > 24h
    |                                              | 3. 回复 ota_progress=downloading
    | <-- MQTT ota_progress --------------------- |
    |                                              | 4. HTTPS GET firmware URL
    |                                              | 5. SHA256 校验
    |                                              | 6. 回复 ota_progress=verifying
    | <-- MQTT ota_progress --------------------- |
    |                                              | 7. 写 OTA 分区
    |                                              | 8. esp_https_ota 切换
    | <-- MQTT ota_progress=ok ------------------- |
    |                                              | 9. esp_restart()
    |                                              |
    | <-- 重启后重连 MQTT -->          | 10. 上报 fw_version=v1.2.3
```

**失败回滚**：
- 校验失败 -> 不写入 OTA 分区, `ota_progress=failed error="sha256_mismatch"`
- 写入失败 -> 不重启, `ota_progress=failed error="flash_write_error"`
- 启动后新固件连续崩溃 3 次 -> 自动回滚上一版 (`esp_ota_mark_app_valid_cancel_rollback`)
